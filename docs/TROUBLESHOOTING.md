# AWOO/KR 트러블슈팅 기록

AWOO/KR을 만들며 겪었거나 신경 쓴 문제를 정리한 문서입니다. 아직 배워가는 입장에서 작성한 기록이며, 문제를 어떻게 바라보고 해결해봤는지 남기기 위한 목적입니다.

## 1. 프론트엔드와 백엔드 분리 배포 후 API 호출 경로 정리

### 상황

프론트엔드는 Vercel, 백엔드는 Render에 따로 배포했습니다. 로컬에서는 API 주소를 직접 호출해도 괜찮았지만, 배포 환경에서는 브라우저에서 백엔드 주소를 직접 호출할 때 CORS와 환경변수 관리가 신경 쓰였습니다.

### 시도한 방법

Next.js의 `/api/*` route를 백엔드 API로 넘기는 proxy처럼 사용했습니다. 브라우저는 프론트엔드의 `/api` 경로로 요청하고, 서버 쪽에서 `BACKEND_API_BASE_URL`을 사용해 Render 백엔드로 전달하도록 구성했습니다.

### 배운 점

- 프론트엔드와 백엔드를 나누어 배포하면 API base URL 관리가 중요했습니다.
- 브라우저에서 직접 백엔드 주소를 호출하는 방식보다, 프론트엔드 서버를 통해 API 경로를 정리하는 방식이 배포 환경을 이해하는 데 도움이 됐습니다.

## 2. Render 무료 인스턴스 cold start

### 상황

Render 무료 인스턴스를 사용하다 보니 첫 요청에서 백엔드가 깨어나는 시간이 걸렸습니다. 사용자가 처음 접속했을 때 응답이 늦어지는 문제가 있었습니다.

### 시도한 방법

백엔드에 `/api/health` endpoint를 두고, GitHub Actions scheduled workflow에서 일정 간격으로 health endpoint를 호출하도록 했습니다.

### 배운 점

- 무료 배포 환경에서는 기능 구현 외에도 서비스가 어떻게 깨어나고 응답하는지 확인해야 했습니다.
- health check endpoint가 있으면 배포 상태를 간단히 확인할 수 있었습니다.

## 3. 익명 게시판에서 작성자 수정/삭제 처리

### 상황

AWOO/KR은 회원가입 기반 서비스가 아니라 익명 게시판에 가깝습니다. 그래서 일반적인 로그인 사용자 id 없이도 작성자가 자신의 글이나 댓글을 수정/삭제할 방법이 필요했습니다.

### 시도한 방법

글과 댓글 작성 시 `editPassword`를 받고, 원문 비밀번호가 아니라 hash 값을 저장했습니다. 수정/삭제 요청 시 입력한 비밀번호를 저장된 hash와 비교하는 방식으로 처리했습니다.

### 배운 점

- 회원 인증이 없는 서비스에서도 작성자 확인 흐름이 필요했습니다.
- 비밀번호 원문을 저장하지 않고 hash로 저장해야 한다는 점을 프로젝트에 적용해볼 수 있었습니다.

## 4. CAPTCHA token 재사용 방지

### 상황

글 작성이나 댓글 작성에 CAPTCHA를 붙였지만, 같은 token을 반복해서 쓰면 의미가 줄어들 수 있다고 생각했습니다.

### 시도한 방법

CAPTCHA token payload에 nonce와 만료 시간을 포함하고, 사용된 nonce를 기록해 재사용을 막는 방식을 써봤습니다.

### 배운 점

- CAPTCHA는 정답 확인뿐 아니라 token의 만료와 재사용 여부도 같이 생각해야 했습니다.
- 작은 보안 기능도 상태 관리가 필요하다는 점을 알게 됐습니다.

## 5. 이미지 업로드와 썸네일 생성

### 상황

이미지 게시판 스타일의 서비스라 이미지 업로드 기능이 필요했습니다. 하지만 원본 이미지만 그대로 저장하면 용량이 커지고, 목록 화면에서 불필요하게 큰 이미지를 불러올 수 있었습니다.

### 시도한 방법

Sharp를 사용해 업로드 이미지를 리사이징하고 썸네일을 생성했습니다. 운영 환경에서는 Supabase Storage에 저장하고, DB에는 storage key와 이미지 메타데이터를 저장했습니다.

### 배운 점

- 파일 업로드는 DB 저장만으로 끝나지 않고, 저장소와 메타데이터를 함께 다뤄야 했습니다.
- 목록 화면과 상세 화면에서 필요한 이미지 크기가 다를 수 있다는 점을 알게 됐습니다.

## 6. 관리자 요청과 CSRF token

### 상황

관리자 페이지는 신고 처리, 숨김, 차단 같은 기능을 다루기 때문에 단순히 URL을 숨기는 것만으로는 부족하다고 느꼈습니다.

### 시도한 방법

관리자 로그인 후 session cookie를 사용하고, 변경 요청에는 CSRF token을 함께 확인하도록 했습니다. DB에는 session token과 CSRF token의 hash를 저장했습니다.

### 배운 점

- 관리자 기능은 로그인 여부뿐 아니라 요청이 의도된 요청인지 확인하는 흐름도 필요했습니다.
- cookie 기반 세션을 쓸 때 CSRF 개념을 같이 공부해볼 수 있었습니다.
